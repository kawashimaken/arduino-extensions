# 02: インターネットラジオ（Uno R3 / W5100 / VS1053）

W5100でHTTPのMP3／AAC音声を受信し、VS1053へ小さな単位で転送して再生する、独立したPlatformIOプロジェクトです。
Arduino Uno R3（ATmega328P）を使用します。両方のシールドのSDカードは使いません。
Webサーバーのサンプルとは別のファームウェアで、操作はシリアルモニターから行います。

## 標準のシールドとピン

標準設定 `RADIO_PIN_PROFILE = 1` は、GeeetechのWikiで配布されている
`MP3-TF.zip` 内の `SFEMP3ShieldConfig.h` の通常のUno向け設定に合わせています。
**VS1053本体のCSはD6、D9はMP3シールドのSDカード用CSです。**
実物のピン配線がこのタイプなら、CSのピンを曲げたり、基板を切断したりする必要はありません。

| Unoのピン | W5100シールド | VS1053シールド |
| --- | --- | --- |
| D2 | — | DREQ（音声データの受け入れ可否） |
| D4 | SDカードCS | 一部の基板ではGPIO1（MIDI起動選択）にも接続 |
| D6 | — | XCS：VS1053制御用CS |
| D7 | — | XDCS：音声データ用CS |
| D8 | — | XRESET：VS1053リセット |
| D9 | — | SDカードCS（使わないのでHIGH） |
| D10 | W5100本体のCS | — |
| D11 / D12 / D13 | SPI MOSI / MISO / SCK | 同じSPIを共用 |

基板のリビジョンによってSPIはICSPヘッダー経由の場合もあります。
CSを分け、SPIトランザクションごとに設定を切り替えて通信します。
SDカードを使わなくても、それぞれのCSを無効状態に保つ必要があります。

### D4とMIDI起動への対処

SparkFun互換の一部シールドは、D4がVS1053のGPIO1にもつながっています。
GPIO1をHIGHにしたままリセットすると、通常のMP3再生ではなくMIDIモードで起動する可能性があります。
このプログラムは、VS1053をハードウェアリセットする間だけD4をLOWに保ち、
SPI通信を始める前にHIGHへ戻します。この間はSPIクロックを出しません。
両方のSDカードは挿さずに使用してください。

### 他の資料のピン番号について

Cirkit Designerの記事のサンプルは `CS=10 / DCS=8 / DREQ=3 / RESET=9` です。
**この例は上のGeeetech配布ライブラリの配線と異なり、CS=D10はW5100と衝突します。**

`include/radio_config.h` に、記事の配線からCSだけをD6へ物理的に移した場合の
`RADIO_PIN_PROFILE = 2` も用意しています。これはコード設定だけでは実現しません。
実際の基板がCS=D10であると分かった場合に限り、ジャンパ等によってD10からCSを分離し、
D6につなぐ必要があります。記事の汎用サンプルだけを根拠に基板を加工しないでください。
標準のGeeetech設定で使う場合は、この変更は不要です。

## 最初の接続と起動

1. Unoの電源を切り、W5100シールドとVS1053シールドを取り付けます。
2. 実物の配線を上の表と照合します。スタック用ヘッダーを使い、LAN端子の金属部分と上側基板の裏面が接触しない高さを確保します。
3. **両方のSDカードスロットを空にします。**
4. W5100を、インターネットにつながったDHCP対応ルーターへLANケーブルで接続します。
5. VS1053のヘッドホン端子にヘッドホンを接続し、最初は耳から外しておきます。
6. このフォルダをVS Code / PlatformIOで開き、Build → Upload → Serial Monitorの順に実行します。
7. シリアルモニターは115200bpsです。起動ログを見逃したらRESETボタンを押します。

音声を外部アンプへ接続する場合は、使用基板のライン出力の仕様に従ってください。
VS1053の **GBUFはGNDではありません**。GBUFを外部機器のGNDへ直接つながないでください。
最初の動作確認は基板のヘッドホン端子で行うのが簡単です。

```powershell
pio run
pio run --target upload
pio device monitor --baud 115200
```

ポートの自動選択に失敗する場合は、`platformio.ini` に実際の `upload_port` / `monitor_port` を設定します。
初期設定ではDHCPでIPを取得します。PC直結などDHCPがない構成は、設定ファイルのサンプル用固定IPをネットワークに合わせて変更してください。
サンプルのIP/MACは架空の設定例です。複数台使う場合はMACを機器ごとに分けます。

## 初期の放送局

サンプルはSomaFMの **Groove Salad / AAC 64kbps** を個人視聴する設定です。
接続先は `include/radio_config.h` の次の3項目です。

```cpp
constexpr char kStationHost[]="ice1.somafm.com";
constexpr char kStationPath[]="/groovesalad-64-aac";
constexpr uint16_t kStationPort=80;
```

PC側でHTTP 200と `Content-Type: audio/aac`、ADTS形式の音声データを確認し、実機でもVS1053がAACとして認識して継続再生することを確認しています。
128kbpsのMP3版 `/groovesalad-128-mp3` も指定できますが、下記のとおりこの構成では受信が追いつかない場合があります。配信先は変更される場合があるため、接続できなくなったら放送元の直接配信URLを確認してください。

対応するのは **HTTPで直接取得できるMP3音声、またはADTS形式のAAC／HE-AAC音声**（`audio/mpeg`、`audio/mp3`、`audio/aac`、`audio/aacp`）です。
HTTPS、HLS（.m3u8）、PLS/M3Uの選局用プレイリスト、HTTPリダイレクトは扱いません。
エラー時にWebページやプレイリストをVS1053へ渡さないよう、HTTPステータスとContent-Typeを確認します。
HTTP/1.0・1.1の200応答とICY 200応答、chunked転送、ICYメタデータの除去に対応しています。
曲名の表示はしません。音声に紛れたメタデータは再生データから取り除きます。

## 操作

シリアルモニターから次の1文字を送信します。改行が付いても構いません。

| コマンド | 動作 |
| --- | --- |
| `p` | 再生開始／再接続。VS1053も再初期化 |
| `s` | 停止・ミュート |
| `+` | 音量を上げる |
| `-` | 音量を下げる |
| `t` | ラジオを止め、約0.4秒のテスト音を鳴らす。再開は `p` |
| `?` | 状態と操作一覧を表示 |
| `d` | 転送速度、受信待ち/DREQ待ちの回数、デコーダーの経過秒数を表示 |

初期音量は減衰値50（約25dBの減衰）です。設定値が小さいほど大きな音になります。
通信切断・データ停止時は約5秒後に再試行します。
テスト音はネットワーク接続なしでもVS1053の認識と出力を切り分けるために使えます。

## ログの見方

通常は次の順に進みます。

```text
VS1053 detected.
Starting Ethernet (DHCP may take 15 s)...
IP: ...
TCP RX buffer bytes=8192
Connecting http://...
Audio response accepted. Buffering...
Buffered bytes=6200. Playing.
```

- `VS1053 not found`：実物のCS/DCS/DREQ/RESET、プロファイル、電源、SPI接続を確認します。ネット接続より先にここを解決します。
- テスト音は出るが再生しない：TCP接続先、HTTPステータス、放送局の配信形式を確認します。
- `HTTP/ICY error=1`：200以外、リダイレクト、または応答形式の問題です。
- `error=2`：ヘッダー不正／長すぎる応答です。`error=3`：MP3／AAC以外のContent-Typeなどです。
- `error=4`：未対応の転送・圧縮方式です。`error=5`：chunked転送の形式不正です。
- `Stream/DREQ stalled`：通信停止かデコーダーの受け入れ停止です。ピンと電源も確認します。
- `State` は `0=VS1053待ち / 1=Ethernet待ち / 2=接続待ち / 3=受信中 / 4=停止` です。

UnoのRAMが小さいため大きなソフトウェアバッファは使わず、W5100とVS1053のバッファを使います。
DHCP更新や再接続の間は音声が一時停止することがあります。多数の局の一覧・Web操作画面は含めていません。

## 検証範囲

PlatformIOのUno向けビルドを確認しています。
初版は実機への書き込み、VS1053認識、DHCP取得、MP3データの継続転送を確認し、ユーザーから音声再生成功の報告を受けています。
音切れ対策版も書き込み・フラッシュ照合を実施し、実機の受信バッファ4KB、約3.4KBの初期蓄積、約36秒間の継続転送を確認しています。
実際の音切れの改善度と長時間の再生安定性は、聴取による確認が必要です。

## 音切れ対策版

- 使用ソケット数を1にし、W5100の受信メモリ8KBをすべてラジオ用TCP接続に割り当てています。UnoのRAMに確保する処理ではありません。
- W5100は受信バッファの**空き容量**をTCPウィンドウとして相手に通知します。
  4KBでは、128kbps（16KB/s）・往復遅延約120msの受信に必要な約2KBの空きを残すと、再生用の余裕は約2KBしか残りません。
  8KBにすることで、ネットワークの揺らぎを吸収できる余裕が約3倍になります。
- 再生開始前に原則6KBをためます（約2KBはTCPウィンドウ用に空けておきます）。最大3秒で待機を打ち切り、受信できたデータで再生を開始します。
- DNSはTCP接続の前に終わるため、1ソケットでも問題ありません。DHCPのリース更新時だけは、再生を止めてソケットを空け、すぐにDHCPと再接続を行います（数秒の中断）。
  中断を避けたい場合は固定IP（`kUseDhcp=false`）にしてください。
- まとめて受信する量を64から128バイトへ増やしています。VS1053へ送る単位は仕様どおり最大32バイトです。
- 10秒ごとの自動状態表示は停止しました。状態は `?` で表示でき、`TCP queued` がW5100の待ちデータ量、`min` が前回の `?` 以降の最小値です。
  音切れの直後に `min` が0付近なら、ネットワーク側の遅延による受信不足が原因です。0から遠いのに音切れする場合は、電源やデコーダー側を疑います。
- 設定は `include/radio_config.h` の `kPrebufferBytes`、`kPrebufferMaxWaitMs`、`kReportIntervalMs` で変更できます。

Ethernet 2.0.2はソケット数をヘッダー内で無条件に定義するため、`configure_ethernet.py` が
生成済みの `.pio/libdeps` 内の定義をガード付きに変更し、プロジェクトの1ソケット設定を有効にします。
ライブラリの版は固定してあり、想定外のヘッダーの場合はビルドを止めます。
`.pio` を消しても、依存ライブラリの再取得後に同じ調整を適用します。ほかのプロジェクトのライブラリは変更しません。

ネットワークの遅延や電源などによる音切れを完全に防げる保証はありません。

初期バッファ量の判定は、ライブラリのキャッシュされた `available()` ではなく、W5100の受信量レジスターを直接確認しています。

## 転送負荷の軽減と診断

ヘッダーの検査後、chunked・ICYメタデータ・Content-Lengthがない通常の連続音声は、
受信バッファから最大32バイトずつVS1053へ直接転送します。バイト単位のコピーとパーサー呼び出しを減らす処理です。
HTTP/ICYの区切り処理が必要な配信は従来のパーサーを使い、デコーダーのDREQ確認は省略しません。

`d` を数秒おきに送ると、区間の `Audio B/s`（VS1053に渡したバイト数/秒）と、
`Decoded seconds`（VS1053が正常にデコードした音声の累計秒数）を確認できます。
128kbps MP3の平均的な必要量は約16000バイト/秒、64kbps AACは約8000バイト/秒です。起動直後の値には接続・蓄積時間も含まれます。
`net-empty polls` と `DREQ-busy polls` は待ちを観測した回数で、音切れの回数そのものではありません。
診断は手動コマンド時だけ出力し、通常再生中の定期ログは増やしていません。

## 低ビットレート局への変更（2026-11-18）

1ソケット・8KB化した後も、128kbps MP3では計測区間の受信量が約5〜13KB/sにとどまり、必要な16KB/sに届きませんでした。
同じ回線のPCでは同じ配信を約29KB/sで受信できたため、W5100側のTCP受信速度が制約と考えられます（原因は未特定）。
そこで初期の局を **64kbps HE-AAC（約8KB/s）** に変更しました。VS1053はADTS形式のAACをそのまま再生できます。

- VS1053のクロック設定（CLOCKF）を `0x6000`（3.0倍）から、メーカー推奨の `0x8800`（3.5倍、必要時に最大4.5倍）に変更しました。HE-AACのデコードにも余裕を持たせる設定です。`d` で読み出し値を確認できます。
- 実機で約2.5分計測し、W5100の待ちデータは常に約6〜7KBあり、切断・停止は起きていません。
- `HDAT1=0x4154` はVS1053がAAC（ADTS）として認識していることを示します。
- 起動直後の最初の接続で `error=2` が出ることがありますが、自動で再接続して再生します。原因は未特定です。
- VS1053への転送量（約7.7KB/s）は、配信の平均ビットレート（HDAT0の値で約8.2KB/s）よりわずかに少なく、
  `Decoded seconds` も実時間の約93%でした。聴いて音切れや音程の違和感が残る場合は、この差が手がかりになります。
